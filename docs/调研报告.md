## 0. 核心发现速览（事实性）

1. **smartdiff 能写回文件**，不是"只能对比"。它有完整的三路合并 + 原子写回，限制在**格式**（仅 SpreadsheetML `.xml`），不在能力。
2. **最有价值的资产是两个引擎，且都与文件格式完全解耦**：`xml_differ.py`（292 行）和 `xml_merger.py` 算法层（约 420 行）是纯字典运算，喂任何格式的解析结果都能跑。实测在 Python 3.13 下 `test_merger` 29/29、`test_differ` 11/11 通过，无需 SVN、无需 Office。
3. **最大缺口不是 Excel 解析，是 SVN 拓扑**：smartdiff 的所有 SVN 操作锚定在单个本地工作副本，只能做「同一路径两个 revision」对比。我们的核心场景「KR/Dev vs JP/Dev」「KR/Dev vs KR/Fix」是**两个不同 URL 的对比**，现有代码一行都不支持。
4. **实测挖出 3 个缺陷**，其中「插入列导致 diff 雪崩」对跨区域对比是致命的（1 列插入 → 12 个假差异），必须在自研时补列匹配能力。
5. **写回限制**：smartdiff 目前只能把合并结果写回 `.xml`；写回 `.xlsx` 需自研，难点在保真（openpyxl 会丢图表/条件格式/数据验证/VBA）。
6. **三路合并语义层已被 smartdiff 解决**（11 种行状态 + 5 种单元格状态 + 决议校验），可直接复用；真正的工程量在写回保真。
7. **LLM 报告原则**：先做确定性 diff，再让 LLM 只做摘要与风险提示；内网数据不能默认发外网。

## 1. 需求背景与场景拆解

- 4 个版本区域（KR/JP/TC/BT），每区有 Dev 与 Fix 两个 SVN 地址，共 **8 个仓库路径**。
- Fix 提交会自动合并回 Dev（区域间不同步），因此对比场景分两类：
- 公式不参与对比，只比较导出的值（与 smartdiff 的 `data_only=True` 读取行为一致）。
- 每个区域下有自己的 Dev（主干分支）与 Fix（线上分支），也会有相同与不同的内容。

| 场景 | 示例 | 难度 | 要点 |
|---|---|---|---|
| 同区域 Dev vs Fix | KR-Fix → KR-Dev | 中 | 需要 revision 基线与 `svn mergeinfo` 判断未合并内容 |
| 同区域不同版本 | KR-Dev r100 vs r120 | 低 | `svn diff` 原生支持 |
| 跨区域同分支 | KR-Dev vs JP-Dev | 高 | 内容本就不同，必须按文件/表/主键做语义对比，不能按行号 |
| 任意两文件夹/文件 | 本地导出目录 | 低-中 | 通用文件夹 diff + Excel 单元格 diff |

短期需求：对比两个 SVN 文件夹差异、对比两个文件差异。
长期需求：Excel Merge；LLM 自动输出对比报告。

## 2. 形态选型考量（网页端 vs 本地端）

| 形态 | 优点 | 缺点 | 适合 |
|---|---|---|---|
| 纯桌面 GUI（WinMerge/ExcelMerge/Beyond Compare） | 上手快、数据最安全、无需部署 | 多区域/多分支管理弱、报告共享难、难接 LLM | 短期应急、单人使用 |
| 本地 Web（localhost） | 界面好、SVN/LLM 都在本机、数据不出内网、免运维 | 默认单机使用 | 中期形态候选 |
| 内网服务器 Web | 多人协作、报告集中、可接 CI/定时任务 | 需要账号体系、SVN 凭据管理、审计、防 SSRF | 团队规模大、长期形态候选 |
| 纯浏览器（无后端，如 SheetJS 前端工具） | 零安装、纯前端 | **无法直接访问 SVN**，只能手动上传文件 | 只做单文件对比，不满足 SVN 场景 |

关键权衡点：
- 策划在 Windows 上已有 TortoiseSVN，浏览器界面学习成本低。
- SVN 操作（`svn diff --summarize`、`svn cat/export`）只能在有 svn 客户端的后端执行，纯前端做不了。
- 数据全程在内网，符合游戏项目配置安全要求。
- 同一套代码后期加鉴权即可升级为内网服务，路径平滑。

> 最终采用形态（本地 GUI / 本地 Web / 内网 Web）需结合团队环境、是否需多人共享、内网 LLM 可用性等因素决策，本报告不在此下结论。

## 4. SmartDiff 代码级评估

对象：`reference/smartdiff`（v1.5.0，MIT，Python 3.8+，约 5,900 行有效代码）
方法：通读全部源码 + 实跑单元测试 + 针对性构造用例验证 3 个疑点
目的：确认哪些部分能直接用于我们的平台

### 4.1 实测记录

```
python tests/test_merger.py   → 29/29 PASS
python tests/test_differ.py   → 11/11 PASS
```

引擎在 Python 3.13 下开箱即跑，无需 SVN、无需 Office。三路合并的 XML 写回 roundtrip、命名空间保真、注释保留、`ExpandedRowCount` 维护均实测通过。

针对 3 个疑点构造了独立验证用例，脚本保留在 `docs/verify/`，可随时复跑：

| 脚本 | 验证内容 | 结果 |
|---|---|---|
| `v1_duplicate_id.py` | 重复 ID 是否导致漏检 | **未漏检**（三轮匹配兜住了） |
| `v2_celltype_fidelity.py` | 合并写回后单元格类型保真 | **发现缺陷**（见 4.5.1） |
| `v3_column_shift.py` | 插入列后的 diff 噪音 | **发现严重缺陷**（见 4.5.2） |

复跑方式：`python docs/verify/v3_column_shift.py`

### 4.2 架构分层（决定了可复用性）

```
解析层    xml_parser.py / xlsx_parser.py
              ↓  统一输出 {sheets:{name:{headers, rows:[{_row, cells:{"A":"值"}}]}}}
算法层    xml_differ.diff_workbooks()          ← 与格式无关
          xml_merger.three_way_diff()          ← 与格式无关
          xml_merger.apply_resolutions()       ← 与格式无关
          xml_merger._compute_sheet_operations() ← 与格式无关（决议 → update/remove/insert）
              ↓
写回层    xml_merger.write_merged_xml()        ← 仅此处绑定 XML
接入层    svn_helper.py / server.py / static/
```

**关键点**：算法层只依赖 `col_to_letter` / `letter_to_col` 两个纯函数和上面那个字典结构。只要我们的 CSV/xlsx 解析器输出同样的结构，两个引擎可以直接调用，**一行不改**。

`_compute_sheet_operations`（L429-500）这一层尤其值得注意——它已经把「用户决议」翻译成了格式中立的三种原语（`update_rows` / `remove_rows` / `insert_rows`）。做 xlsx 写回时，只需实现一个 openpyxl 版的 `_apply_sheet_ops`，不需要重新设计合并语义。

### 4.4 能力覆盖矩阵：我们要的 vs smartdiff 有的

| 我们的需求 | smartdiff 现状 | 缺口 |
|---|---|---|
| 对比两个 SVN **文件夹**（跨区域 KR vs JP） | ❌ **完全不支持** | `get_changed_files_between_revisions(path, rev_old, rev_new)`（svn_helper.py L323）只接受**一个** target + 两个 revision，执行 `svn diff --summarize -r OLD:NEW <target>`。跨 URL 需 `svn diff --summarize --old=URL1 --new=URL2`，代码里无任何 `--old`/`--new` 使用。 |
| 对比同区域 Dev vs Fix | ❌ 不支持 | 同上，且缺 `svn mergeinfo`——判断"Fix 哪些改动还没合进 Dev"必须用它，代码中无任何 mergeinfo 调用。 |
| 对比同一路径两个版本 | ✅ 已实现 | `/api/diff/overview` 可用，是唯一贴合的场景。 |
| 对比任意两个本地文件 | ⚠️ 半支持 | 引擎支持，但接入层强制文件必须在"当前工作区"内（`_safe_workspace_path` L308）。任选两文件对比需改接口。 |
| 8 个仓库统一管理 | ❌ 不支持 | config 里 workspaces 是列表，但同时只有一个 `active_workspace` 生效，是"切换"不是"并列"。 |
| CSV 支持 | ❌ 无 | 全项目只认 `.xml/.xlsx/.xls`（`_is_excel_binary` L43、`SUPPORTED_EXTENSIONS`）。实际产物是 CSV。 |
| xlsx 写回合并 | ❌ 无 | 仅 `.xml` 能写回。 |
| 差异报告导出 | ⚠️ 弱 | 界面展示为主，无明显导出；如需交付策划/QA，需加导出。 |
| 本地 Web 端 | ✅ 已实现 | Flask SPA，端口 5566，中文界面，可作前端基础参考。 |
| LLM 报告 | ❌ 无 | 无任何相关代码。但 diff 输出已是结构化 JSON，是很好的 LLM 输入。 |
| SVN 认证 | ❌ 无 | 无 `--username/--password` 处理，完全依赖本机 SVN 凭据缓存。内网多仓库场景需补。 |
| 批量对比性能 | ⚠️ 隐患 | `/api/diff/overview`（L864）是**串行 for 循环**，每个文件 2 次 `svn cat` 网络往返，单请求阻塞返回、无进度、无缓存。几百个文件的目录对比会超时。 |

> 一句话概括缺口：smartdiff 为「一个人、一个工作副本、盯本地改动和历史版本」设计；我们要的是「多人、8 仓库、跨仓库横向对比」。**引擎能复用，拓扑要重做。**

### 4.5 实测发现的缺陷

#### 4.5.1 合并写回时新增行的单元格类型退化为 String

**证据**（`docs/verify/v2_celltype_fidelity.py` 实跑输出）：

```
Row3: [('String','1002'), ('String','盾'), ('Number','22')]   ← 更新已有单元格，Number 保留 ✓
Row4: [('String','1003'), ('String','弓'), ('String','30')]   ← 远端新增行，Number 退化为 String ✗
```

**根因**：`_build_row`（L638）和 `_set_cell_value`（L620）在创建新 `<Data>` 节点时硬编码 `ss:Type="String"`。更新已有节点时只改 text 不动 type，所以旧单元格没事。

**影响**：接受远端新增行后，数值字段在文件里变成字符串类型。若导表工具按 `ss:Type` 判类型，会导致导出结果类型错误或导表失败。

**附带风险**：原 `Type="Number"` 的单元格若被合并成非数值内容，type 不会跟着改，Excel 打开时会提示文件损坏并尝试修复。

**结论**：自研写回层必须做类型推断，不能照搬。

#### 4.5.2 列结构不同时 diff 雪崩（跨区域场景致命）

**证据**（`docs/verify/v3_column_shift.py` 实跑输出）：

```
场景：KR 与 JP 数据完全一致，仅 JP 在第 3 列插入了一个 Desc 列
真实语义差异：1 列新增，0 处数据变更
引擎检出：12 个 modified_cells   ← 全是假差异
```

**根因**：`_diff_sheet`（xml_differ.py L252）按**列字母**对齐单元格（`set(old_cells) | set(new_cells)`），`merged_headers`（L229）只是取较长的那个表头，**完全没做列名映射**。插入一列后，其后所有列整体错位。

**影响**：这正是跨区域对比（KR vs JP）的典型情况——不同区域的表结构大概率有增删列。按现有算法，输出会被假差异淹没，工具直接不可用。

**结论**：**必须新增列匹配层**——按表头名做列映射（而非列位置），识别列的增/删/改名/移动。这是 smartdiff 完全没有、我们必须自写的核心能力。行匹配它做了三轮，列匹配它做了零轮。

#### 4.5.3 合并插入的行一律追加到表尾

**根因**：`_apply_sheet_ops`（L665-669）对 `insert_rows` 执行 `current_max += 1` 后 append。

**影响**：接受远端新增行后，该行落在文件末尾而非原有位置。配置表通常按 ID 排序，会造成：① 与远端文件行序不一致，下次对比又是差异；② SVN diff 噪音变大；③ 策划肉眼核对困难。

**结论**：属设计取舍不是 bug，但我们的场景应改为**按 ID 有序插入**。

### 4.6 三路合并方案调研（纯方案对比，不含路线推荐）

**三路合并定义**：以 BASE（共同基线）/ MINE（本地）/ THEIRS（远端）三方对比，按"只有我改→取我、只有对方改→取对方、两边同改→直接用、两边异改→冲突人工决议"逐格判定。

| 方案 | 许可证 | 结论 |
|---|---|---|
| smartdiff `xml_merger.py`（本地已有） | MIT | 单元格级+行级合并语义、决议模型、写回保真可整体移植到 xlsx |
| [Suture](https://github.com/WyattAu/suture)（Rust 语义合并，含 `suture-driver-xlsx`） | Apache-2.0 | 备选，需 PoC：文档对 xlsx 支持级别自相矛盾（Cell-level vs Binary），仓库 0 star、个人项目 |
| [eMerge](https://github.com/yuyixiaoxiang/electron_excel_merge)（Tauri 桌面三方合并） | 未声明 | 交互/流程参考，不能直接改造 |
| 3DM / xml_3dm（结构感知 XML 三路合并） | 见项目 | 借鉴 insert/delete/update/move/copy 冲突分类 |

### 4.8 真实样本（ArenaPeak.xlsm）结构实测

为验证待确认 #5/#3，实测了 `reference/table/ArenaPeak.xlsm`（带宏工作簿，11 个 sheet：main/Base/LocalRank/Rank/RankMatch/Map/HeroGroup/EqualModeConfig/CheckIn/SeasonTarget/Banner）。

**统一表结构（文件内全部 sheet 一致；已确认全库所有表/文件统一）**：
- 固定 **7 行表头块**，数据从第 **8 行**开始（1-indexed）：
  - 行1：中文显示名；行2：**字段代码名**（英文标识，如 `Id`/`SeasonNum`）；行3：**类型**（`uint32`/`string`/`uint32[]`/`[uint=uint]`/`int32[]` 等）；行4：**导出端**（`All`/`Client`/`Server`/**`None`**）；行5：空行分隔；行6：中文备注；行7：作者。
- **主键 = 第一列（A 列）**，数据行 8+；其行2代码名恒为 `Id`/`id`（行1显示名不固定：IndexID/indexID/ID/流水ID 等）。
- `main` 表是**目录表**：列 `sheetName → tbxName`（如 `Base → ArenaPeak_Base`），即 XLSX 子表与导出 CSV 文件名的映射。

**对方案的直接影响**：
1. **#5 表头/主键约定已确认**：解析器配置为「表头 7 行、数据起第 8 行、主键=首列（按行2代码名 `Id` 识别）」。**该约定已确认全库所有表统一**（不限于 ArenaPeak 单文件），因此 smartdiff 的 ID 自动检测可直接套用，无需逐表配置。
2. **#3 跨区域差异可大幅缓解**：列由稳定的英文代码名（行2）标识，KR vs JP 即便增删/重排列，只要按**代码名**匹配列（而非列位置），就不会触发缺陷 4.5.2 的"列错位 diff 雪崩"。真实差异集中在数据值（赛季数值、奖励串等），正是我们想检出的；行1/行6 的中文在表头块内、不参与数据 diff，不会污染结果。
3. **D2 CSV↔XLSX 映射已可确定**：CSV 列 = 导出端≠`None` 的 XLSX 列，顺序同 XLSX；回写时按行2代码名定位 XLSX 列、按主键定位行（第8行+记录序）。`main` 表提供 sheet→CSV 文件名映射。

**关键坑：openpyxl 无法打开此真实文件**
- `openpyxl.load_workbook` 直接抛 `ValueError: Duplicate position 0.0`（样式表 `gradientFill` 有重复停靠点，openpyxl 严格解析拒绝）。
- 含义：原"openpyxl 加载→改 `.value`→保存"的写回设想、以及 smartdiff 的 `xlsx_parser.py`（同样依赖 openpyxl）在此类真实文件上**会打不开**。
- **建议改走 XML 底层**：读用自写 unzip + XML 解析（已验证可读，见下方"读回验证"）；写回用"解压→改 `sheetN.xml` 中目标单元格 `<v>`→重压"的值级编辑。**完全不碰样式表**，既绕开解析 bug，又 100% 保留格式（合并单元格/条件格式/图表全不动）。这同时消解了风险 #13 的保真担忧——因为我们根本不重建结构，只改值。smartdiff 引擎只需我们解析器输出的统一字典，不依赖 openpyxl。

> 读回验证脚本（解压直读，绕过 openpyxl）已跑通，可复现为后续自研解析器的骨架。

## 5. 风险清单

1. **xlsx 是 zip 二进制**，文本 diff 完全无效，必须先解析单元格。
2. **"值"和"公式"要分开比**：公式相同但缓存值不同、或公式不同但值相同，都是常见噪音（`data_only` 双通道读取）。
3. **行插入/删除会错位**：必须用主键（ID）匹配行，否则整表全是"假 diff"；移动行还需 LIS/相似度算法识别。
4. **表头/类型/注释行的位置不固定**：需要可配置的表头行、数据起始行列（游戏配置表常是"列名/类型/注释/数据"多行头）。
5. **大文件性能**：openpyxl 全量读入慢、内存高，需 `read_only` 模式或转 CSV/pandas；前端展示需虚拟滚动。
6. **编码坑**：CSV/TBX 可能是 GBK/UTF-8/带 BOM，行尾 CRLF/LF 不一致，对比前需统一规范化。
7. **TBX 是内部格式，必须先拿样例确认**。通用 "TBX" 指术语库 XML（TermBase eXchange），与游戏项目的 TBX 很可能不是一回事。
8. **SVN 认证**：后端集成 svn 时要处理凭据（优先用 SVN 认证缓存或只读账号），不要把明文密码写进配置。
9. **分支模型复杂**：Fix 自动合入 Dev 后，Dev 可能含 Fix 全部变更 + Dev 独有变更；对比 Dev/Fix 必须选好 revision 基线，并用 `svn mergeinfo --show-revs eligible` 看哪些还没合并。跨区域对比预期差异大，需按表/按 key 过滤。
10. **LLM 幻觉**：LLM 可能编造数值；架构上必须"先确定性 diff，再让 LLM 只做摘要"，并让报告标注 AI 生成。
11. **数据出境**：内网配置数据不能默认发到外网 LLM；需内网模型或走公司审批通道。
12. **开源项目成熟度**：smartdiff 功能契合但只有个位数 star，属个人项目，需把核心逻辑吸收进自研代码而非直接依赖；ExcelMerge 已停更且许可证不明确；Suture 需 PoC。
13. **xlsx 写回保真风险（已消解）**：原以为合并单元格/样式/条件格式易丢；因确定走 XML 底层值级写回（只改 `<v>`、不碰样式表），格式 100% 保留，此风险消除，只需做"改值后重压仍能被 Excel 打开"的 roundtrip 验证。
14. **smartdiff 合并写回的类型退化（4.5.1）与插入行追加表尾（4.5.3）**：自研写回层必须做类型推断与按 ID 有序插入。
15. **openpyxl 无法打开真实策划表（已转化为写回方案）**：实测 `ArenaPeak.xlsm` 因样式表 `gradientFill` 重复停靠点，openpyxl 抛 `Duplicate position 0.0`。原"openpyxl 加载→改值→保存"写回设想与 smartdiff 的 `xlsx_parser` 在此类文件上不可用。由此确定走 XML 底层解析/值级写回（见 4.8），反因祸得福——既绕开 bug 又 100% 保格式。

## 6. 待确认信息（影响后续方案设计）

### 已确认（2026-08-04）

1. ✅ **配置表实际格式 = 真正的 `.xlsx`**（非 SpreadsheetML 2003 `.xml`）。
   → 写回层不能用 smartdiff 的 XML 写回路径；且真实策划表 openpyxl 打不开（风险 #15），故须走 **XML 底层值级写回**（见 4.8）。
2. ✅ **对比基准 = SVN 上的 CSV；写回目标 = XLSX**。
   CSV 一定会随配置上传到 SVN（即 SVN 上版本化的是 CSV），因此直接对比 SVN 上的 CSV 即可，无需解析 XLSX 做 diff；合并/决议产出的结果再**值级写回**到 XLSX。写回走 XML 底层（解压 → 改 `sheetN.xml` 目标单元格 `<v>` → 重压），不依赖 openpyxl、不碰样式表，100% 保留格式（见 4.8）。

**已确认项的架构含义**：
- diff/merge 在 CSV（纯文本）层做，避开 xlsx 的 zip 解析；smartdiff 的 diff/merge 算法层（格式无关）可直接复用，只需补一个「CSV → 统一字典」的解析器（输出与 `xml_differ` 一致的 `{sheets:{name:{headers, rows:[{_row, cells:{...}}]}}}` 结构，单表即可）。
- 写回从「完整三路 xlsx 合并引擎」降级为「值级单元格回填」，原风险 #13（xlsx 写回保真会丢图表/条件格式/数据验证/VBA）**已消解**——因走 XML 底层只改 `<v>`、不重建结构、不碰样式表，格式 100% 保留（见 4.8）。
- 缺陷 4.5.2（列错位 diff 雪崩）**不因此消失**：跨区域对比仍需按列名映射而非列位置，列匹配层仍须自研。
- 衍生待确认项见下方 D1–D4。

### 衍生待确认（由「对比 CSV + 写回 XLSX」策略引出，决定该策略是否可行）

- **D1. ✅ XLSX 可访问性（已确认）**：写回需要的 XLSX 文件本体可访问。工具能取到它来做写回。
  - *残留子问题已并入 D4 并确认*：XLSX 与 CSV 同在 SVN 提交（形态丙），工具取 SVN 上的 xlsm 写回、不自动提交。
- **D2. ✅ CSV↔XLSX 映射规则（已由 ArenaPeak.xlsm 实测 + 全库约定确认）**：CSV 列 = 导出端≠`None` 的 XLSX 列、顺序同 XLSX；回写按行2代码名定位列、按主键定位行（第8行+记录序）；`main` 表提供 sheet→CSV 文件名映射。详见 4.8。7 行表头全库统一已确认（见 #5），映射规则成立。
- **D3. ✅ XLSX 公式处理（已确认）**：无视公式，写回时**直接以值覆盖**单元格（原本是公式的格子也只写值、不再保留公式逻辑）。两点明确结论：① 写回方案无需保留公式，XML 底层改 `<v>` 即满足，逻辑简化；② 若某些格子原本是公式、其派生值依赖别处，写回为静态值后该依赖消失——策划侧已知并接受此取舍。
- **D4. ✅ 写回后的闭环（已确认：形态丙）**：已确认 **CSV 与 XLSM 都提交在 SVN 上**，且**策划提交时两者一起提交**。据此闭环定为：

  - **工具只做"取 XLSX → 写回值 → 交还"**，不申请 SVN 写权限、不自动 commit（= 形态丙：XLSX 在 SVN 供工具读取写回，提交由策划执行）。
  - **单源真相 = XLSX**：策划以 xlsm 为编辑源、导出 csv 后两者一并提交；工具写回 xlsm 后，csv 由策划重新导出（或工具一并回写 csv）保持一致。
  - **工具 SVN 权限 = 读权限即可**，规避 xlsm 类二进制冲突与认证复杂度，闭环最稳。

  参考（三态对比，确认落在形态丙）：

  | 维度 | 形态甲：XLSX 也提交 SVN（工具自动提交） | 形态乙：XLSX 仅本地 | **形态丙（已确认）：XLSX 在 SVN，策划提交** |
  |---|---|---|---|
  | 写回自动化 | 全自动 | 半自动 | 半自动（工具写回，策划提交） |
  | 工具 SVN 权限 | 需写权限 + 认证 | 仅读 | **仅读** |
  | 取 XLSX 做写回 | SVN 直接取 | 需策划提供 | **SVN 直接取** |
  | SVN 冲突 | 有 | 无 | **无（工具不写 SVN）** |
  | 策划审核体验 | 好 | 中 | **好（直接开 XLSX 看结果）** |
  | 工具复杂度 | 高 | 低 | **低** |

  **闭环后的 CSV/XLSX 一致性（设计注意）**：写回 xlsm 后，SVN 上的 csv 仍是旧值。因 csv 由 xlsm 导出，需保证二者同步——方案设计阶段二选一：① 工具在写回 xlsm 的同时**也回写 csv 对应单元格**（同一份决议、两个落点）；② 工具只写 xlsm，由策划**重新导出 csv** 再一并提交。无论哪种，"对比在 CSV、写回在 XLSX"的策略不变，仅多一个 csv 同步动作。
