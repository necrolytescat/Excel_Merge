# `m2.batch.v1` 批量 Diff 契约

> 状态：D1 已评审通过；D2 已实现并通过真实双分支编排验收
> 版本：`m2.batch.v1`
> 日期：2026-08-05
> 实施边界：本文件继续作为冻结契约；D2 实现与验收见 `docs/M2-05-STAGE-D2-REVIEW-HANDOFF.md`

## 1. 结论与范围

`m2.batch.v1` 是 M1 文件级候选与现有 `m2.diff.v1` 之间的批量编排契约：

```text
冻结 endpoint_id + Revision
-> 服务端按 M1 规则重建完整候选集
-> 每个 modified 候选独立执行现有单工作簿 Diff
-> 每个合法 m2.diff.v1 独立持久化
-> 批量项只保存摘要和不透明 result_ref
```

首版归入 **M2-07**，范围仅限单机、单个冻结快照对的可靠批量 Diff。M3 保留通用或分布式任务队列、优先级、跨节点 Worker、长期历史报告、通知和跨区域聚合，不重复实现本契约。

本契约不修改以下已冻结行为：

- `source=left`、`target=right`；
- `m2.diff.v1` 是唯一的单工作簿明细契约；
- `m2.diff.v1.workbook.status=partial/failed` 是 HTTP 200 的合法业务结果；
- `left_only/right_only/read_error` 不调用语义 Diff；
- 不重新读取 `HEAD`，不接受本地目录、SVN URL、凭据或浏览器候选清单；
- 不扫描 `TableCsv` 猜测归属，不执行 SVN 写操作；
- 单个工作簿失败不得终止其他工作簿。

## 2. 契约集合与严格校验

| 用途 | `schema_version` |
|---|---|
| 创建请求 | `m2.batch-create.request.v1` |
| 任务查询/命令响应 | `m2.batch.v1` |
| 取消请求 | `m2.batch-cancel.request.v1` |
| 重试请求 | `m2.batch-retry.request.v1` |
| 单项结果 | 现有 `m2.diff.v1` |

所有请求和 `m2.batch.v1` 的每一级对象均使用严格模型：未知字段拒绝、枚举值区分大小写、整数不接受字符串或布尔值、时间统一为 UTC RFC 3339 `Z` 格式。破坏性字段变更必须升级 schema version。

## 3. 创建请求与任务身份

### 3.1 创建请求

```json
{
  "schema_version": "m2.batch-create.request.v1",
  "request_id": "a7e47a49-3308-4d10-936c-bbb80e4547b3",
  "source": {
    "endpoint_id": "KR_FIX_KR-Fix-1.0.0.0",
    "revision": 123456
  },
  "target": {
    "endpoint_id": "KR_FIX_KR-Fix-1.0.1.0",
    "revision": 123789
  }
}
```

| 字段 | 规则 |
|---|---|
| `request_id` | 客户端生成 UUID；同时用于日志关联和创建幂等，不是任务 ID |
| `source/target.endpoint_id` | 已登记、启用且互不相同的具体端点 ID |
| `source/target.revision` | 正整数冻结 Revision；不接受 `HEAD`、日期或字符串 |
| `task_id` | 服务端生成 UUID；创建请求不能指定 |

创建请求故意不包含 `snapshot_id`、候选路径、候选状态、SVN URL、本地目录、物理路径、凭据或并发参数。当前 M1 没有服务端 `snapshot_id`，因此后台准备阶段必须在请求给定的两侧具体 Revision 上，按 M1 规则重新读取 `Table` Excel 清单并生成完整权威候选集。浏览器缓存的候选只用于展示，不是输入或安全边界。

### 3.2 幂等规则

- 同一所有者范围内，`request_id` 唯一；并发重复创建也只能产生一个 `task_id`。
- 首次创建返回 HTTP 202；相同 `request_id` 与相同规范化输入重放时返回 HTTP 200 和原任务。
- 相同 `request_id` 携带不同 source、target 或 Revision 时返回 HTTP 409 `BATCH_IDEMPOTENCY_CONFLICT`。
- 幂等记录至少保留到任务 30 天保留期和后续 7 天墓碑期结束；墓碑删除后不保证继续去重。
- 任务一旦创建，输入身份不可修改。重试会创建新任务，不复写原任务。

## 4. `m2.batch.v1` 顶层模型

完整示例见 `m2.batch.v1.example.json`。

| 字段 | 类型 | 规则 |
|---|---|---|
| `schema_version` | literal | 固定 `m2.batch.v1` |
| `task_id` | UUID | 服务端任务身份 |
| `request_id` | UUID | 创建或重试命令的幂等身份 |
| `retry_of_task_id` | UUID/null | 仅重试任务非空 |
| `status` | enum | 任务状态，见第 6 节 |
| `source` / `target` | object | 仅含 `endpoint_id`、正整数 `revision` |
| `candidate_source` | object | 服务端候选准备状态和清单指纹 |
| `execution_policy` | object | 本任务实际采用的冻结执行限制 |
| `progress` | object | 服务端按单项状态实时派生，不由客户端累计 |
| `items` | array | 权威候选清单；准备完成前为空 |
| `errors` | array | 仅任务级错误；单项编排错误放在对应 item |
| `created_at` / `updated_at` | datetime | 始终存在，UTC |
| `preparation_started_at` | datetime/null | 首次进入 `preparing` 时写入 |
| `prepared_at` | datetime/null | 候选清单原子提交后写入 |
| `started_at` | datetime/null | 第一个可执行单项开始时写入 |
| `cancel_requested_at` | datetime/null | 取消命令被接受时写入 |
| `finished_at` | datetime/null | 进入任务终态时写入且不再改变 |
| `expires_at` | datetime/null | 终态为 `finished_at + 30 天`；活动任务为空 |

`candidate_source` 字段：

| 字段 | 类型 | 规则 |
|---|---|---|
| `kind` | literal | 固定 `m1_server_revalidated` |
| `ruleset` | literal | 固定 `m1.table-excel-candidates.v1` |
| `scope` | enum | `all` 或 `retry_subset` |
| `status` | enum | `pending/preparing/ready/failed` |
| `manifest_sha256` | string/null | `ready` 时必填；对按 `ordinal` 排序的规范候选 JSON 计算 |

`execution_policy` 首版固定值：

```json
{
  "global_concurrency": 2,
  "per_task_concurrency": 1,
  "item_timeout_seconds": 600,
  "automatic_retry_attempts": 0,
  "max_recovery_attempts": 1
}
```

## 5. 候选与单项模型

### 5.1 权威候选生成

服务端使用现有 M1 口径：相对逻辑 `TABLE` 根目录的规范路径精确匹配，扩展名仍限 `.xlsx/.xlsm/.xls`，路径按稳定顺序排序。

状态优先级与当前 M1 一致：

1. 仅 source 存在：`left_only`；
2. 仅 target 存在：`right_only`；
3. 两侧存在但任一侧读取失败：`read_error`；
4. 两侧读取成功且 SHA-256 不同：`modified`；
5. 两侧读取成功且 SHA-256 相同：不是候选，不进入任务。

每个候选保存两侧文件事实，不保存 SVN URL 或物理路径：

```json
{
  "path": "AtlasConfig.xlsm",
  "status": "modified",
  "source": {
    "exists": true,
    "size_bytes": 125430,
    "content_sha256": "...",
    "read_error": null
  },
  "target": {
    "exists": true,
    "size_bytes": 126004,
    "content_sha256": "...",
    "read_error": null
  },
  "fingerprint_sha256": "..."
}
```

不存在的一侧仍返回对象，`exists=false`，其余字段必须为 null。`read_error` 只含 `{code, message}`。候选指纹覆盖 path、status、两侧 exists/size/hash/error code，不覆盖可变时间或展示文案。

### 5.2 单项字段

| 字段 | 类型 | 规则 |
|---|---|---|
| `item_id` | UUID | 在任务内稳定 |
| `retry_of_item_id` | UUID/null | 重试来源；原始任务为空 |
| `ordinal` | int | 从 0 开始，按候选规范路径稳定排序 |
| `candidate` | object | 第 5.1 节权威候选 |
| `status` | enum | 单项状态，见第 6 节 |
| `diff_status` | enum/null | `unchanged/modified/partial/failed`；只在引擎已产生合法 `m2.diff.v1` 时存在 |
| `diff_error_count` | int/null | 从对应 `m2.diff.v1.summary.error_count` 复制，不复制错误明细 |
| `result_ref` | string/null | 仅 `succeeded/business_failed` 必填 |
| `result_sha256` | string/null | 对未压缩、规范 UTF-8 `m2.diff.v1` 字节计算 |
| `result_size_bytes` | int/null | 未压缩 JSON 字节数 |
| `result_expires_at` | datetime/null | 与任务 `expires_at` 相同 |
| `orchestration_error` | object/null | 仅 `orchestration_failed` 必填，结构为 `{code,message,retryable}` |
| `reason_code` | enum/null | `skipped/cancelled` 必填 |
| `attempt_count` | int | 每次获得执行租约加 1；未执行为 0 |
| `recovery_count` | int | 因进程中断重新排队的次数，最大 1 |
| `created_at` / `updated_at` | datetime | 始终存在 |
| `started_at` / `finished_at` | datetime/null | 按状态写入；终态必须有 `finished_at` |

字段组合必须满足：

- `succeeded` <=> `diff_status` 为 `unchanged/modified`，且 result 四字段完整；
- `business_failed` <=> `diff_status` 为 `partial/failed`，且 result 四字段完整；
- `orchestration_failed` 不得有 `diff_status/result_ref`，必须有 `orchestration_error`；
- `skipped` 仅用于三类不可执行候选，`reason_code` 分别为 `BATCH_CANDIDATE_LEFT_ONLY`、`BATCH_CANDIDATE_RIGHT_ONLY`、`BATCH_CANDIDATE_READ_ERROR`；
- `cancelled` 仅用于从未开始的项，`attempt_count=0`，`reason_code=BATCH_CANCELLED_BEFORE_START`；
- `queued/running` 不得预先填充 result、业务状态或终态时间。

`partial/failed` 的详细 Sheet、行、字段和错误仍只存在于被引用的 `m2.diff.v1` 中，批量层不得复制或改写。

## 6. 状态机

### 6.1 任务状态

| 状态 | 含义 | 终态 |
|---|---|---:|
| `queued` | 任务已持久化，尚未准备候选 | 否 |
| `preparing` | 服务端重建并校验 M1 候选集 | 否 |
| `running` | 候选已冻结，正在或等待逐项执行 | 否 |
| `cancelling` | 取消已持久化，等待当前运行项到安全边界 | 否 |
| `completed` | 全部项终态，无业务失败、编排失败或取消；允许有不可执行项 `skipped` | 是 |
| `completed_with_failures` | 全部项终态，至少一个 `business_failed/orchestration_failed`，且未接受取消 | 是 |
| `cancelled` | 已接受取消且无运行项；已完成结果保留，未开始项已标记取消 | 是 |
| `failed` | 候选准备或任务级持久化/状态一致性发生致命错误，任务不能安全继续 | 是 |

合法转换：

```text
queued -> preparing | cancelling | failed
preparing -> running | completed | cancelling | failed
running -> completed | completed_with_failures | cancelling | failed
cancelling -> cancelled | failed
terminal -> (no transition)
```

零候选任务从 `preparing` 直接进入 `completed`。`failed` 必须有任务级 `errors[]`；若候选总数已知，进入 `failed` 前必须停止领取新项并将所有非终态项原子收敛为 `orchestration_failed`。终态不可复活，重试只能创建子任务。

### 6.2 单项状态

| 状态 | 含义 | 终态 |
|---|---|---:|
| `queued` | 可执行的 `modified` 项等待租约 | 否 |
| `running` | 当前租约持有者正在物化、Diff 或保存结果 | 否 |
| `succeeded` | 得到 `unchanged/modified` 合法结果 | 是 |
| `business_failed` | 得到 `partial/failed` 合法结果 | 是 |
| `orchestration_failed` | 未生成可读取的合法结果 | 是 |
| `skipped` | `left_only/right_only/read_error`，不调用 Diff | 是 |
| `cancelled` | 取消时尚未开始 | 是 |

合法转换：

```text
candidate prepared -> queued              (modified)
candidate prepared -> skipped             (left_only/right_only/read_error)
queued -> running | cancelled
running -> succeeded | business_failed | orchestration_failed
running -> queued                          (仅租约过期恢复，最多 1 次)
terminal -> (no transition)
```

取消不强杀 `running` 项；该项完成后按真实结果进入三个执行终态之一。单项超时是 `orchestration_failed`，错误码 `BATCH_ITEM_TIMEOUT`，不会伪造成引擎 `failed`。

## 7. 进度口径

`candidate_source.status != ready` 时，`total_items=null`、`ratio=null`，其余计数为 0。候选清单原子提交后，`total_items` 固定且不再变化。

`progress` 字段：

| 字段 | 计算规则 |
|---|---|
| `total_items` | 权威候选数量；准备前为 null |
| `queued_items` | `status=queued` |
| `running_items` | `status=running` |
| `succeeded_items` | `status=succeeded` |
| `business_failed_items` | `status=business_failed`，包括引擎 `partial/failed` |
| `orchestration_failed_items` | `status=orchestration_failed` |
| `skipped_items` | `status=skipped` |
| `cancelled_items` | `status=cancelled` |
| `processed_items` | 五类终态计数之和 |
| `ratio` | `processed_items / total_items`；准备前为 null；零候选完成时为 1.0 |

候选准备完成后必须始终满足：

```text
total_items = queued + running + succeeded + business_failed
              + orchestration_failed + skipped + cancelled
processed_items = succeeded + business_failed + orchestration_failed
                  + skipped + cancelled
0 <= ratio <= 1
```

进度从持久化单项状态派生，不维护另一份可漂移计数器。

## 8. API

### 8.1 路由

| 方法与路由 | 成功响应 | 用途 |
|---|---|---|
| `POST /api/diff/batches` | 202 新建 / 200 幂等重放，body 为 `m2.batch.v1` | 创建任务 |
| `GET /api/diff/batches/{task_id}` | 200，body 为 `m2.batch.v1` | 查询和刷新恢复 |
| `GET /api/diff/batch-results/{result_ref}` | 200，body 直接为 `m2.diff.v1` | 按需读取单工作簿明细 |
| `POST /api/diff/batches/{task_id}/cancel` | 202，body 为 `m2.batch.v1` | 请求取消 |
| `POST /api/diff/batches/{task_id}/retry` | 202 新建 / 200 幂等重放，body 为新任务 `m2.batch.v1` | 创建重试子任务 |

查询可以返回 `ETag`；客户端携带 `If-None-Match` 时允许返回 304。首版不冻结列表、删除、优先级、暂停或 WebSocket API。

### 8.2 取消请求

```json
{
  "schema_version": "m2.batch-cancel.request.v1",
  "request_id": "8e54e23d-6705-4e41-aa2c-3b77c1a6c1f0",
  "reason": "用户取消本次全量比对"
}
```

`reason` 可选，最大 256 字符，只用于审计。取消命令自身按 `request_id` 幂等。服务端必须先持久化 `cancel_requested_at`，再停止领取新项并把所有 `queued` 项标记为 `cancelled`。已完成项及其 `result_ref` 保留。任务已终态时返回 409 `BATCH_TASK_NOT_CANCELLABLE`；不能把一个已经自然完成的任务改名为 cancelled。

### 8.3 重试请求

```json
{
  "schema_version": "m2.batch-retry.request.v1",
  "request_id": "6db0fb89-0a6e-494e-b1b2-7b7aab6e65fb",
  "item_ids": [
    "12287e7f-56d8-4d58-b939-a4f5706c99fa"
  ]
}
```

- 仅终态任务可重试；重试创建新 `task_id`，并填写 `retry_of_task_id/retry_of_item_id`。
- 省略 `item_ids` 时，默认选择 `orchestration_failed`、`cancelled` 以及 `candidate.status=read_error` 的 `skipped` 项。
- 显式 `item_ids` 还允许选择 `business_failed`，用于部署修复后重新运行；相同冻结输入下它通常是确定性结果，因此不默认选择。
- `succeeded` 和 `left_only/right_only` 的 `skipped` 项不可重试。
- `item_ids` 必须唯一、属于原任务且最多 500 个；任一项不合法时整次请求返回 422，不创建部分子任务。
- 子任务继承原任务的端点与 Revision，并再次服务端校验所选路径；客户端不能替换输入。
- 原任务及原 `result_ref` 不改变。

### 8.4 错误结构

沿用现有 Web 编排错误结构，不把内部路径、异常堆栈或凭据返回给客户端：

```json
{
  "error": {
    "code": "BATCH_TASK_NOT_FOUND",
    "message": "批量任务不存在"
  }
}
```

| HTTP | 典型错误码 |
|---:|---|
| 400 | `BATCH_INVALID_REQUEST`、`BATCH_UNSUPPORTED_SCHEMA` |
| 403 | `BATCH_TASK_FORBIDDEN`、`BATCH_RESULT_FORBIDDEN` |
| 404 | `BATCH_ENDPOINT_NOT_FOUND`、`BATCH_REVISION_NOT_FOUND`、`BATCH_TASK_NOT_FOUND`、`BATCH_RESULT_NOT_FOUND` |
| 409 | `BATCH_IDEMPOTENCY_CONFLICT`、`BATCH_TASK_NOT_CANCELLABLE`、`BATCH_TASK_NOT_RETRYABLE` |
| 410 | `BATCH_TASK_EXPIRED`、`BATCH_RESULT_EXPIRED` |
| 422 | `BATCH_ENDPOINT_DISABLED`、`BATCH_ENDPOINTS_MUST_DIFFER`、`BATCH_ITEM_NOT_RETRYABLE` |
| 500 | `BATCH_STORAGE_UNAVAILABLE`、`BATCH_ORCHESTRATION_FAILED` |

引擎 `partial/failed` 和单项编排失败都不是任务查询 API 的 HTTP 失败；它们由 200 `m2.batch.v1` 中的单项状态表达。

## 9. `result_ref`

- 格式为 `m2r_` 加 22 个 base64url 无填充字符，正则 `^m2r_[A-Za-z0-9_-]{22}$`，随机熵至少 128 bit。
- `result_ref` 是不透明定位符，不是本地路径、SVN 地址、任务/单项 ID 编码或授权凭据。
- 每个已生成合法 `m2.diff.v1` 的单项使用独立 ref；`partial/failed` 同样必须有 ref。
- 读取成功直接返回原 `m2.diff.v1`，不得套批量包装或重写字段；可用 `ETag` 返回 `result_sha256`。
- 未知 ref 返回 404 `BATCH_RESULT_NOT_FOUND`；已过期墓碑返回 410 `BATCH_RESULT_EXPIRED`；存在但无权读取返回 403 `BATCH_RESULT_FORBIDDEN`。
- ref 不能替代授权。当前单用户部署的所有者范围是服务端内部 `local`；接入认证后，任务与结果绑定创建者主体并强制同主体或管理员读取。所有者字段不接受客户端提交，也不在 v1 响应中泄漏。

## 10. 持久化、清理与重启恢复

### 10.1 存储决定

首版采用单机持久化：

- 状态根目录由 `EXCEL_MERGE_BATCH_STATE_DIR` 配置；本地默认 `<project>/var/m2-batch`，不得位于静态资源目录或可再生 `.cache`；
- SQLite `batch.sqlite3` 保存任务、候选、单项、命令幂等、租约、ref 映射和墓碑，启用 WAL、外键和事务；
- 每个结果独立保存为 `results/<task_id>/<item_id>.json.gz`，内容是 `serialize_diff_json()` 的 UTF-8 字节经 gzip 压缩；
- 路径是服务端内部实现，不得进入 API；原始 Excel/CSV 不持久化到任务仓库，请求级物化目录仍按现有规则清理。

结果提交顺序固定为：临时文件写入 -> 校验 JSON/schema/SHA-256 -> flush/fsync -> 原子重命名 -> SQLite 事务写入 ref 与终态。数据库未提交前 ref 不可见；启动恢复清除没有结果记录引用的孤立文件。进度由单项表查询派生，避免任务计数与单项状态不一致。

### 10.2 保留与清理

- 任务进入终态后保留 30 天，任务和结果使用同一 `expires_at`；活动任务不按年龄清理。
- 清理器在进程启动时执行一次，此后每 6 小时执行；同一时刻只有一个清理租约持有者。
- 到期后先事务写入墓碑并使查询/结果读取返回 410，再删除结果文件和明细行；墓碑继续保留 7 天后删除。
- 清理不得删除非终态任务、有效结果、当前租约文件或任何 SVN/源 Excel/CSV。
- 单个文件删除失败要记录并留待下轮重试，不得使其他任务不可查询。

### 10.3 重启恢复

- Worker 领取单项时写入 60 秒租约并每 20 秒续租；结果提交必须携带当前租约 token，过期 Worker 的迟到提交被拒绝。
- `queued` 保持等待；`cancelling` 在重启后继续取消收敛；终态保持不变。
- 租约过期的 `running` 项先清理本次临时物化和未提交结果，再转回 `queued`，`recovery_count += 1`；最多自动恢复 1 次。
- 第二次进程中断或恢复校验失败时进入 `orchestration_failed`，错误码 `BATCH_ITEM_RECOVERY_EXHAUSTED`，其他项继续。
- 已原子提交的结果不重复执行；只存在孤立结果文件而无数据库提交的情况视为未完成，删除孤立文件后按恢复规则处理。
- 候选清单必须一次性原子提交。`preparing` 重启时若清单未提交则重新准备；若已提交则直接从已存清单继续，绝不重新读取 `HEAD`。

## 11. 并发、超时与失败隔离

- 全服务实例的工作簿执行并发上限为 2，不是每个进程各 2；通过 SQLite 租约统一协调。
- 单任务并发上限为 1，以避免一个大任务占满服务；调度按任务创建时间轮转。
- 单项 600 秒超时覆盖 SVN 数据集物化、Diff 和结果保存；请求级临时目录在成功、异常、超时和恢复路径都清理。
- 首版没有普通自动重试；只有进程中断触发一次恢复。业务失败和可预期编排失败等待显式重试 API。
- 每个单项使用独立临时目录、异常边界、结果文件和事务。一个单项的 SVN、解析外编排、超时或存储失败只更新该单项。
- 引擎返回 `partial/failed` 时必须先保存完整合法 JSON，再把单项标记为 `business_failed`；不能转换为 `orchestration_failed`。
- 结果保存失败时不得发布 `result_ref`，单项为 `orchestration_failed`，错误码 `BATCH_ITEM_RESULT_STORE_FAILED`。
- 任务级致命失败之外，调度循环不得因单项异常停止领取后续项。
